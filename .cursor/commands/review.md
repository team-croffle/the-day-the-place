브랜치 작업이 끝난 뒤, 커밋하기 전에 변경을 리뷰한다.

## 절차

1. 커밋된 범위는 `git diff master...HEAD --stat`으로 본다. 아직 커밋 전이면 `git diff`와 `git diff --cached`를 본다.
2. `.ai/AGENTS.md`, `.ai/CODEMAP.md`의 함정, 이번 작업의 `.ai/history/`를 읽는다. 화면을 건드렸으면 `.ai/design-drafts/`의 해당 화면을 본다.
3. 아래 관점으로 점검한다.
4. 문제만 보고한다. 고치지 않는다.

## 관점

### 보안

- API 키·토큰·비밀번호가 응답, 로그, 커밋에 남는가. 실패 로그에 요청 URL이 들어가는가
- `.env`나 `.ai/`를 커밋에 넣었는가
- 사용자 데이터를 ID만 바꿔 조회·수정할 수 있는가
- 클라이언트가 보낸 값을 검증 없이 신뢰하는가

### 제품 계약

- 지도 장소에 미술관·영화관이 들어가거나, 좌표 없는 장소가 남는가
- 특별전이 박물관·기념관·전시관이 아닌 기관을 남기는가. 종료된 전시를 상태에 넣거나 지우지 않는가
- 전시정보(통합)을 수집해 저장하는가. 화면은 그 API를 직접 읽고, 겹치는 수집 행은 빼야 한다
- 네이버 뉴스로 전시를 모으는가. 종료일이 없는 글을 규칙이 통과시키는가. 규칙이 읽은 글을 Gemini에 다시 보내는가. Gemini 답의 날짜·기관이 본문에 없는데 남기는가
- 이미지 파일을 우리 서버에 복사하는가. 원문 문단을 소개로 저장하는가
- `DRY_RUN`이 DB나 수집 커서를 쓰는가

### 정합성

- 스키마를 바꿨는데 Drizzle 마이그레이션이 빠졌는가. 수집기가 표를 직접 만드는가
- 서버와 웹이 `shared`의 같은 판정·상수를 쓰지 않고 따로 거르는가
- 같은 전시가 제목만 조금 달라 두 장으로 남는가
- 수집 커서를 처리가 끝나기 전에 최신 글 번호로 당겨, 못 본 글을 남기는가

### 명세 대조

- `.ai/ROADMAP.md`나 공개 `ROADMAP.md`와 다르게 동작하는가
- 시안에서 확정된 경로(지도·박물관·유적지·특별전)와 다른 경로를 만들었는가
- 요청에 없는데 임의로 넣은 동작이 있는가

### 아키텍처

- 공용 타입이 `shared` 밖에 중복 정의됐는가
- 수집기가 INSERT/DELETE 말고 마이그레이션을 소유하는가
- 웹 화면을 바꿨는데 그 흐름을 확인하지 않았는가

### 네이밍

- 파일명·함수명·타입명이 실제 동작과 다른가

## 출력

문제마다:

- 파일과 라인
- 무엇이 문제인지
- 어떤 상황에서 드러나는지
- 심각도: 막음(머지 불가) / 고쳐야 함(다음 브랜치 전) / 알아둘 것(당장은 괜찮음)

## 원칙

- 잘 된 점은 쓰지 않는다.
- 코드 근거를 든다. 추측으로 쓰지 않는다.
- 문제가 없으면 없다고 말한다.
- 수정은 사용자 확인 후에 한다. 리뷰에서 바로 고치지 않는다.
